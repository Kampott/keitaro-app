# Руководство пользователя

Интерфейс Adrobot состоит из двух вкладок: **Create Campaign** и **Edit Campaign**.

Главное правило: в **Create Campaign** кампания сразу создаётся в Keitaro, а в **Edit Campaign** изменения офферов сначала сохраняются в локальной копии. В Keitaro они попадают только после нажатия **Upload to Keitaro**.

## Вход

Если в `.env` заданы `APP_BASIC_AUTH_USER` и `APP_BASIC_AUTH_PASSWORD`, при первом обращении к интерфейсу откроется окно **Доступ к Adrobot**. Введите логин и пароль из `.env`.

Значения хранятся только в памяти страницы: после обновления вкладки придётся войти снова. Напишите их в браузере, а не в исходниках и не в URL.

## Create Campaign

Форма создания находится слева, карточка **Результат создания** — справа.

### Обязательные поля

| Поле | Что делать |
|---|---|
| **Name \*** | название кампании, до 255 символов |
| **GEO \*** | поиск по коду или названию страны; можно выбрать несколько. Показано до 12 строк, выбранные страны остаются в списке и дублируются чипсами над ним. Чипс с `×` убирает страну |
| **Offers \*** | офферы из каталога Keitaro, до 20. Подсказки появляются сразу при фокусе, поиск по названию или ID, задержка 150 мс. Уже выбранные офферы скрываются. Стрелки выбирают вариант, `Enter` подтверждает, `Escape` закрывает список |
| **Domain \*** | активный домен из справочника; используется и для tracking URL |
| **Group \*** | группа кампаний. Можно выбрать существующую или создать новую полем **Новая группа** и кнопкой **Создать группу**, не выходя из формы |
| **Source \*** | источник трафика из справочника |

Поля Domain, Group и Source сначала получают значения по умолчанию из `.env` (`KEITARO_DEFAULT_*`), иначе подставляется первая строка справочника.

Кнопка **Create Campaign** блокируется на время запроса, поэтому повторный клик не создаст вторую кампанию. Если что-то не заполнено, появится уведомление:

> Заполните поля Name, GEO, Offers, Domain, Group и Source.

### Что происходит после создания

Backend:

1. Проверяет, что домен, группа, источник и все офферы существуют и активны.
2. Генерирует уникальный alias из 8 символов.
3. Создаёт кампанию в Keitaro.
4. Создаёт два потока: `GEO to Google` (`schema=redirect`, фильтр `country` accept и адрес из `GOOGLE_REDIRECT_URL`) и `Offer` (`schema=landings` с выбранными офферами).
5. Распределяет 100% между офферами целыми долями и читает созданную структуру обратно из Keitaro.
6. Сохраняет локальную копию кампании, потоков и офферов.

В карточке **Результат создания** показываются:

- название, ID Keitaro и alias;
- **Tracking URL** — кликабельная ссылка или пояснение, что URL не сформирован;
- выбранные Domain, Group, Source, Offers и GEO;
- таблица потоков с колонками `ID | Name | Schema | Position`.

Если Keitaro создал кампанию, но не удалось прочитать её или записать локальную копию, в результате появится предупреждение `local_sync_failed`. В этом случае перейдите в **Edit Campaign** и выполните Fetch вручную — кампания в Keitaro уже существует, повторно создавать её не нужно.

## Edit Campaign

### Выбор кампании

Поле **Кампания Keitaro** ищет по названию, alias или ID. Список кампаний загружается один раз при открытии вкладки и фильтруется локально; отдельной кнопки обновления списка в интерфейсе нет. На backend список кэшируется на 30 секунд и может быть обновлён через API параметром `refresh=true`.

При выборе кампании:

- если локальной копии ещё нет, backend выполняет Fetch и создаёт копию — появится уведомление `Локальная копия кампании ... создана через Fetch`;
- если копия уже есть, открывается сохранённое локальное состояние, а не данные Keitaro.

Кнопка **Fetch from Keitaro** перечитывает кампанию и заменяет локальную копию. Если в копии есть локальные изменения, откроется окно подтверждения:

- заголовок: **Перезаписать локальные изменения?**;
- сообщение: «Есть локальные изменения. Fetch перезапишет их. Продолжить?»;
- кнопка **Продолжить** повторяет запрос с принудительным обновлением.

Если поток в данный момент отправляется в Keitaro, Fetch завершится ошибкой `BUSY` — дождитесь окончания Upload.

### Потоки

Раздел **Потоки** показывает все потоки кампании. Выбрать можно только поток со схемой `landings`. Остальные потоки видны серыми, не кликаются и не получают фокус с клавиатуры. Если редактируемых потоков нет, показывается сообщение:

> Потоки не редактируются: схема не landings. Остальные потоки показаны серыми выше.

Над таблицей офферов находятся:

- `Поток #{id} · позиция {position}` и бейдж статуса (`Синхронизировано`, `Изменено локально`, `Отправка`, `Ошибка`);
- `Сумма shares (от backend): {N}` — frontend только отображает значение и не пересчитывает доли сам;
- пометка `конфигурация некорректна`, если `shares_valid: false`;
- чекбокс **Force upload**;
- кнопка **Upload to Keitaro**;
- последняя ошибка и название текущей операции, если операция выполняется.

### Таблица офферов

| Колонка | Что означает |
|---|---|
| `Offer ID` | ID оффера в Keitaro |
| `Offer Name` | название из каталога; для неизвестного ID — `Offer #{id} (название недоступно)` |
| `Share` | целое число от 1 до 100, поле без нативных стрелок. Изменение сохраняется по `Enter` или кнопке `Save` |
| `Fixed` | закреплённая доля: backend не пересчитывает её автоматически |
| `Local Status` | локальное состояние: `Inactive`, `Read-only`, `Error`, `Uploading`, `Modified`, `Active` |
| `Keitaro State` | состояние, пришедшее из Keitaro; пустое значение показывается как `—` |
| `Actions` | кнопка `Delete` |

`Read-only` — информационная пометка: раньше она блокировала мутации, теперь нет. Изменять можно любые потоки и офферы; блокировки демо-режима и `FLOW_READONLY` удалены.

### Shares и Fixed

Backend хранит shares целыми числами, рабочий минимум — `MIN_SHARE = 1`. Сумма активных долей потока должна быть 100.

- Ручной ввод **Share** делает оффер `Fixed` и сохраняет введённое значение как приоритетное.
- Чтобы снять Fixed, отдельно снимите галочку **Fixed**. Нельзя одним запросом задать share и одновременно выключить Fixed — сначала снимите галочку, затем измените число.
- Остальные незакреплённые офферы пересчитываются автоматически: доли делятся поровну, остаток распределяется детерминированно по весам.
- После удаления оффера незакреплённые доли сбрасываются и делятся заново: например, `34/33/33` превращается в `50/50`. Закреплённые доли сохраняются.
- Если закреплённых долей слишком много или все офферы закреплены с суммой не 100, backend вернёт ошибку, и локальные данные останутся без изменений.

Если `Сумма shares (от backend)` не равна 100 или появилась пометка `конфигурация некорректна`, исправьте доли до Upload.

### Добавление оффера

Поле **Найти оффер для добавления** работает так же, как в форме создания: подсказки из каталога по названию или ID, повторно выбранные офферы скрываются.

В Edit Campaign дополнительно можно добавить **произвольный положительный Offer ID**, даже если оффера нет в каталоге. Когда в поиске остаётся только число, появляется вариант `Добавить оффер #ID` с подсказкой «по ID, название может быть недоступно». В таблице такой оффер отображается как `Offer #ID (название недоступно)`.

После добавления shares всего потока пересчитываются.

### Delete и Deleted Offers

Кнопка **Delete** не удаляет оффер из базы навсегда, а перемещает его в локальный раздел **Deleted Offers**. Перед удалением открывается окно подтверждения:

- заголовок: **Удалить оффер?**;
- сообщение: «Оффер #ID будет перемещён в Deleted Offers. Доли остальных офферов будут пересчитаны.»;
- кнопка **Удалить**.

В таблице **Deleted Offers** можно нажать **Restore**. Оффер вернётся в активные, его прежняя доля и Fixed не используются — share назначается заново.

Удалённые офферы участвуют только в локальном состоянии: Upload отправляет в Keitaro только активные офферы потока. Последний оффер можно удалить локально и отправить пустой список — Keitaro принимает `offers: []`, это подтверждённый владельцем сценарий. Чтобы вернуть оффер, нажмите **Restore** в Deleted Offers.

### Fetch и Upload

- **Fetch from Keitaro** перечитывает кампанию, обновляет потоки, офферы, их состояния и сбрасывает локальные правки.
- **Upload to Keitaro** отправляет активные офферы выбранного потока. Перед отправкой backend проверяет, что кампания и поток не изменились в Keitaro и что сумма shares корректна. Пустой список офферов разрешён.
- **Force upload** нужен, если поток изменился в Keitaro (`REMOTE_CHANGED`). При включённом чекбоксе открывается подтверждение **Force upload** с кнопкой **Перезаписать**. Если `REMOTE_CHANGED` пришёл неожиданно, интерфейс предложит то же подтверждение отдельным окном **Поток изменился в Keitaro**. Force перезаписывает офферы потока в Keitaro локальной версией.

После Upload backend делает контрольное чтение потока. Если частичный `PUT /streams/{id}` затёр другие поля, отправляется полный `PUT` с сохранённым набором полей потока. Если офферы не подтвердились, локальный статус становится `Ошибка`, а причина показывается в строке `Последняя ошибка`.

Локальные правки, сделанные во время отправки, не считаются отправленными: после успешного Upload поток остаётся `Изменено локально`, и его нужно отправить ещё раз.

## Подтверждения и уведомления

Все опасные действия подтверждаются внутренним окном с ролью `alertdialog`, а не системным `window.confirm`:

- перезапись локальных изменений при Fetch;
- удаление оффера;
- Force upload и подтверждение `REMOTE_CHANGED`.

Окно закрывается кнопкой **Отмена**, нажатием `Escape` или кликом по фону. Пока операция выполняется, элементы формы заблокированы, а вверху показывается название операции. Уведомления появляются справа внизу и исчезают через 6 секунд.

## Что нельзя делать в интерфейсе

- Восстановить архивную кампанию Keitaro: в UI есть только Restore для оффера в локальной копии.
- Менять адрес Keitaro или API-ключ: это делается только в `.env` на сервере.
- Редактировать потоки со схемой не `landings`.
- Работать с несколькими пользователями и ролями: приложение использует одну Basic auth-учётную запись и один Keitaro API-ключ.
