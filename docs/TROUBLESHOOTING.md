# Диагностика и устранение неисправностей

Гайд по типовым проблемам локальной/контролируемой эксплуатации Adrobot. Порядок раздела: от запуска и доступа к конкретным операциям. Для каждой проблемы — симптом, причина и действие.

Начните с базовой проверки:

```bash
docker compose ps
curl -s http://127.0.0.1:8080/healthz
docker compose logs -f backend
```

Ожидаемый health-check: `{"status":"ok","db":true,"keitaro_configured":true}`. Поле `status` всегда `ok` — смотрите флаги.

Ошибки backend приходят в формате `{"code": "...", "message": "...", "details": {...}}`. В UI они показываются как `КОД: сообщение`. Полный справочник кодов — в [API.md](API.md#коды-ошибок).

## Контейнеры не поднимаются

**Симптом.** `docker compose up` падает, один из сервисов в статусе `Exited` или `unhealthy`.

**Действия:**

1. `docker compose logs backend`, `docker compose logs db`, `docker compose logs frontend`.
2. Проверьте `.env`: он должен существовать в корне проекта (`cp .env.example .env`). Секреты оттуда подхватывает Compose.
3. Убедитесь, что порты `8000`, `8080`, `5433` не заняты другими процессами. Все привязки — только к `127.0.0.1`.
4. Если backend падает сразу после старта с ошибкой авторизации — см. раздел [Авторизация](#авторизация).
5. Пересоберите образы после изменения кода: `docker compose up -d --build`. В Compose нет bind mount для исходников.

## `db=false` в health-check

**Симптом.** `/healthz` отвечает, но `db: false`; запросы к `/api/*` падают с ошибками подключения к PostgreSQL.

**Причины и действия:**

- Контейнер `db` не healthy: `docker compose ps`, `docker compose logs db`. Дождитесь `pg_isready`.
- Неверный `DATABASE_URL` при запуске backend вне Compose. Внутри Compose хост БД — `db`, порт `5432`; с хоста — `127.0.0.1:5433`.
- База удалена или переименована. Пересоздайте контейнер: `docker compose up -d --force-recreate db` (данные в volume `pgdata` сохранятся) либо восстановите из дампа — см. [Эксплуатацию](OPERATIONS.md#резервное-копирование-и-восстановление).
- После замены `POSTGRES_*` в `.env` пересоздайте `db`: `docker compose down && docker compose up -d` (внимание: локальная БД при смене имени/пользователя будет другой).

## `keitaro_configured=false` в health-check

**Симптом.** `/healthz` показывает `db: true`, но `keitaro_configured: false`; запросы к Keitaro возвращают `KEITARO_NOT_CONFIGURED` (503).

**Действия:**

1. Проверьте в `.env` значения `KEITARO_BASE_URL` и `KEITARO_API_KEY` — оба должны быть заполнены.
2. Пересоздайте backend, чтобы он перечитал окружение: `docker compose up -d --force-recreate backend`.
3. Убедитесь, что `KEITARO_BASE_URL` указан без `/admin` и `/admin_api/v1`. Иначе backend получит HTML вместо JSON и появятся ошибки `KEITARO_BAD_RESPONSE`.
4. Проверьте ключ без записи в трекер: `GET /api/keitaro/ping` (см. [API.md](API.md#get-apikeitaroping)).

## Авторизация

**Симптом.** Браузер показывает окно **Доступ к Adrobot**, а API отвечает `401 UNAUTHORIZED` с заголовком `WWW-Authenticate: Basic`.

**Причины и действия:**

- Введены неверные логин/пароль: используйте значения `APP_BASIC_AUTH_USER` и `APP_BASIC_AUTH_PASSWORD` из `.env`. Учётные данные живут только в памяти вкладки — после обновления страницы нужно войти снова.
- Basic auth включён, но вы обращаетесь к API через `curl` без `-u`: `curl -u "$APP_BASIC_AUTH_USER:$APP_BASIC_AUTH_PASSWORD" http://127.0.0.1:8000/api/geo`.
- Backend не стартует в production без пары логин/пароль: это намеренный fail-closed. Заполните оба значения в `.env` и пересоздайте контейнер.
- `/healthz` требует авторизацию — это ошибка конфигурации: в коде он открыт. Проверьте, что запрос идёт именно на `/healthz`, а не на `/api/healthz`.
- Разработка без логина возможна только при `APP_ENV=development`; в production-окружении авторизация обязательна.

## Keitaro недоступен или отклоняет запросы

Ошибки приходят с кодом `KEITARO_*`. Первый шаг — `GET /api/keitaro/ping`: он проверяет URL и ключ, не изменяя данные.

| Код | Что означает | Действие |
|---|---|---|
| `KEITARO_UNREACHABLE` (502) | сеть, таймаут или исчерпанные повторы GET | проверьте доступность трекера с хоста Docker, DNS, фаервол, корректность `KEITARO_BASE_URL`; повтор только GET (до 3 попыток) |
| `KEITARO_AUTH` (502) | Keitaro отклонил ключ или редакцию | проверьте `KEITARO_API_KEY`, убедитесь, что у редакции Keitaro есть Admin API; ключ записан в `.env` без лишних пробелов и кавычек. В development при добавлении оффера по ID ошибка не блокирует операцию: оффер сохраняется с названием из ID; в production неизвестный ID вернёт `INVALID_REFERENCE` (422) |
| `KEITARO_NOT_FOUND` (404) | объект не найден в трекере | проверьте ID кампании/потока/оффера; при Fetch несуществующей кампании backend вернёт `NOT_FOUND` |
| `KEITARO_VALIDATION` (422) | Keitaro отклонил тело запроса | читайте `message` и `details` — Keitaro возвращает описание полей; проверьте обязательные поля и активные справочники |
| `KEITARO_BAD_RESPONSE` (502) | неожиданная форма ответа | почти всегда неверный `KEITARO_BASE_URL` (с `/admin`) или несовместимая версия Admin API; сверьтесь с [контрактом](keitaro_contract.md) |

**Важно:** при ошибке чтения Keitaro локальные данные не меняются. При ошибке создания потока кампания архивируется компенсационно. Повторно создавать кампанию вручную не нужно — сначала проверьте трекер.

## Справочники пусты или не обновляются

**Симптом.** Списки Domain, Group, Source, Offers пусты или не показывают свежие изменения в Keitaro.

**Причины и действия:**

- Офферы кэшируются на 60 секунд, список кампаний Keitaro — на 30 секунд. Подождите или перезапустите backend.
- В справочниках показываются только активные домены и офферы. Проверьте состояние объектов в Keitaro.
- Список кампаний в UI фильтруется локально и не имеет кнопки обновления. В API есть `GET /api/keitaro/campaigns?refresh=true` — он сбрасывает кэш.
- Если в Keitaro изменился API-ключ или адрес, пересоздайте backend.
- При создании группы через `POST /api/keitaro/groups` поле `name` не должно быть пустым или длиннее 255 символов.

## Создание кампании падает

| Код | Причина | Действие |
|---|---|---|
| `INVALID_REFERENCE` (422) | не найден домен, группа, источник или активный оффер; в production — попытка добавить оффер, которого нет в каталоге | обновите справочники в UI и выберите ID из списка; офферы должны быть активны. Произвольные ID доступны только при `APP_ENV=development` |
| `INVALID_SHARES` (422) | дубли офферов, share вне диапазона | проверьте выбранные offer_ids, используйте уникальные ID |
| `KEITARO_VALIDATION` (422) | Keitaro отклонил создание, в том числе из-за повтора alias (3 попытки) | повторите создание с другим именем; если причина не alias — сверьте тело запроса с логами |
| `CAMPAIGN_CREATE_FAILED` (502) | не удалось создать поток или структура не совпала | кампания уже архивирована компенсационно; разберите `details` в ответе и логах, не создавайте копию вручную |
| `CREATE_UNKNOWN_RESULT` / `AMBIGUOUS_ALIAS` / `KEITARO_LIST_INCOMPLETE` (502) | ответ на POST потерян, поиск по alias не дал однозначного результата | проверьте трекер по alias из `details`; повторный POST backend не выполняет |

**Симптом.** Создание прошло, но в карточке результата `local_sync_failed: true` или предупреждение о локальной копии.

**Действие.** Кампания в Keitaro уже создана. Откройте **Edit Campaign**, выберите её и выполните Fetch вручную. Повторно создавать кампанию не нужно.

## Fetch не работает

| Код | Причина | Действие |
|---|---|---|
| `LOCAL_CHANGES` (409) | в локальной копии есть изменения, а `force=false` | в UI подтвердите окно **Перезаписать локальные изменения?** — запрос повторится с `force=true`. Или сначала отправьте изменения через Upload |
| `BUSY` (409) | поток в статусе `uploading` | дождитесь окончания Upload, затем повторите |
| `NOT_FOUND` (404) | нет локальной копии или кампании в Keitaro | для Editing выберите кампанию из списка — backend создаст копию автоматически; для прямого `fetch` проверьте ID |
| `KEITARO_UNREACHABLE` / `KEITARO_BAD_RESPONSE` (502) | сетевая ошибка или неожиданный ответ | локальные данные не тронуты; см. раздел про Keitaro выше |
| `LOCAL_DB_ERROR` (500) | ошибка записи локальной копии | проверьте БД и логи backend; транзакция откачена, Keitaro не изменён |

**Симптом.** После Fetch потоки или офферы исчезли из таблицы.

**Причина.** В Keitaro офферы со `state != active` переносятся в **Deleted Offers**, а исчезнувшие потоки получают `state=deleted` и скрываются из UI (данные сохраняются в БД). Восстановите оффер кнопкой **Restore** в локальной копии.

## Проблемы со shares

**Симптом.** `Сумма shares (от backend)` не равна 100 или поток помечен «конфигурация некорректна».

**Причины и действия:**

-Backend считает shares целыми числами, минимум `MIN_SHARE = 1`. Frontend только отображает сумму и не пересчитывает доли.
- Ручной ввод Share делает оффер `Fixed`. Если закреплено слишком много долей, снимите Fixed с части офферов (отдельным запросом/галочкой).
- Нельзя одним PATCH задать `share` и одновременно `is_fixed: false` — backend вернёт `INVALID_REQUEST` (422). Сначала снимите Fixed, затем измените число.
- Пустой PATCH тоже запрещён (`INVALID_REQUEST`).

| Код | Причина | Действие |
|---|---|---|
| `FIXED_SUM_EXCEEDS_100` (422) | сумма Fixed больше 100 | уменьшите или снимите часть закреплённых долей |
| `FIXED_SUM_MUST_BE_100` (422) | все офферы закреплены, но сумма не 100 | исправьте закреплённые доли до ровно 100 |
| `INFEASIBLE_SHARES` (422) | не хватает долей, чтобы дать каждому свободному офферу минимум | снимите лишние Fixed или удалите часть офферов |
| `INVALID_SHARES` (422) | дубль оффера или share вне диапазона | проверьте активные офферы потока |
| `DUPLICATE_OFFER` (409) | оффер уже активен в потоке | выберите другой ID или сначала удалите текущий |

**Симптом.** После удаления оффера доли не «сложились» заново.

**Ожидаемое поведение.** При удалении незакреплённые доли сбрасываются и делятся заново: `34/33/33 → 50/50`. Закреплённые доли сохраняются. Restore возвращает оффер как новый — прежние share и Fixed не используются.

## Upload не работает

| Код | Причина | Действие |
|---|---|---|
| `REMOTE_CHANGED` (409) | поток изменился в Keitaro после последнего Fetch/Upload | сделайте Fetch для сверки или включите **Force upload** и подтвердите перезапись. Force заменяет офферы потока локальной версией |
| `CAMPAIGN_ARCHIVED` (409) | кампания в Keitaro архивирована или не найдена | восстановить кампанию в UI нельзя; проверьте трекер. Локальные данные остаются |
| `BUSY` (409) | поток уже отправляется | дождитесь завершения, повторите |
| `INVALID_SHARES` (422) | некорректные доли | см. раздел про shares |
| `KEITARO_BAD_RESPONSE` (502) | контрольное чтение вернуло неожиданные данные | проверьте логи и контракт; локальные офферы и shares не меняются |

**Симптом.** В потоке удалены все офферы, но Upload завершается успешно.

**Ожидаемое поведение.** Пустой список разрешён: в Keitaro отправляется `offers: []`. Это подтверждённый владельцем сценарий. Чтобы вернуть офферы, используйте **Restore** в Deleted Offers или добавьте новые.

**Симптом.** Статус потока «Ошибка», в строке «Последняя ошибка» — текст ошибки.

**Действие.** Причина записана в `sync_logs` и в `last_error` потока. Исправьте причину и повторите Upload. Если ошибка случилась после перевода в `uploading`, статус автоматически становится `error`; при перезапуске backend зависшие `uploading` тоже переводятся в `error`.

**Симптом.** Upload прошёл успешно, но поток остался «Изменено локально».

**Причина.** Во время отправки были внесены новые правки: `revision` изменился, и backend намеренно не считает их отправленными. Повторите Upload после завершения правок.

**Симптом.** В Keitaro после partial PUT «потерялись» другие поля потока.

**Ожидаемое поведение.** Backend делает контрольное чтение и, если хэш потока без offers изменился, отправляет полный PUT с сохранённым `remote_payload`. Если и после этого офферы не подтвердились, статус становится `error` — проверьте логи и [архитектуру](ARCHITECTURE.md#upload).

## Проблемы интерфейса

**Симптом.** Поток серый и не выбирается.

**Причина.** В интерфейсе для редактирования выбираются только потоки со схемой `landings`. Остальные доступны только для просмотра. Через API мутации и Upload разрешены для любых потоков: ограничение относится к интерфейсу.

**Симптом.** Не открывается окно подтверждения, вместо него системный диалог браузера.

**Причина.** В приложении используется внутреннее окно с ролью `alertdialog`, а не `window.confirm`. Если видите системный диалог — обновите страницу/кэш браузера: сборка устарела. Окно закрывается `Escape`, кнопкой **Отмена** или кликом по фону.

**Симптом.** Оффер из каталога не находится по ID.

**Причина.** Подсказки ищут по названию или ID только среди активных офферов (кэш 60 с). В **Edit Campaign** можно добавить произвольный положительный ID вручную — появится вариант `Добавить оффер #ID` с пометкой `название недоступно`.

**Симптом.** После обновления страницы снова нужен логин.

**Причина.** Basic auth хранится в памяти вкладки и намеренно не сохраняется в localStorage/cookie. Войдите снова.

**Симптом.** UI показывает старые данные справочников или списка кампаний.

**Причина.** Кэш backend (60 с для офферов, 30 с для кампаний). Подождите, перезапустите backend или вызовите `GET /api/keitaro/campaigns?refresh=true`.

**Симптом.** В консоли браузера ошибки `CORS` или `404` на `/api/*`.

**Причина.** Обращение напрямую к frontend-порту минуя nginx, либо неверный путь. API доступен через `/api/` на `8080` или напрямую на `8000`. Проверьте `nginx.conf`: он проксирует только `/api/` и `/healthz`.

## База данных и миграции

**Симптом.** После обновления кода API отвечает ошибками «no such column» / «relation does not exist».

**Действие.**

```bash
docker compose exec backend alembic current
docker compose exec backend alembic upgrade head
docker compose exec backend alembic current
```

Текущая ревизия — `0003 (head)`. Backend выполняет миграции при старте сам; ручной запуск нужен только если контейнер не пересоздавался.

**Симптом.** Нужно откатить данные.

**Действие.** Восстановите дамп PostgreSQL из [Эксплуатации](OPERATIONS.md#резервное-копирование-и-восстановление). `alembic downgrade` удалит таблицы локальной копии и не затронет Keitaro — применяйте его только при крайней необходимости. После восстановления сделайте Fetch, чтобы сверить состояние с трекером.

## Тесты

**Симптом.** Тесты падают с `createdb` / `permission denied`.

**Действие.** Проверьте права `POSTGRES_USER` и доступность БД (`127.0.0.1:5433` с хоста или `db:5432` внутри Compose). Тесты используют отдельную БД `<DATABASE_URL>_test` и создают её при необходимости.

**Симптом.** Падают тесты моделей или `IntegrityError` вне транзакции.

**Причина.** Используется SQLite вместо PostgreSQL. SQLite не поддерживается: тесты работают только с PostgreSQL и через SAVEPOINT.

**Симптом.** Много неожиданных `KEITARO_*` в тестах.

**Действие.** Убедитесь, что `.env` не подменяет тестовые переменные: `conftest.py` задаёт поддельные `KEITARO_BASE_URL` и `KEITARO_API_KEY` через `monkeypatch`. Живой Keitaro в тестах не вызывается.

Подробнее — [Тестирование](TESTING.md).
